# Nod 사용성 테스트 계획 (5명)

승인 설계 원칙 9가지(`src/rules.ts`)는 지금까지 테스트 코드로만 확인했습니다. 이 테스트는 사람이 실제로 그 구조를 이해하고 믿는지 봅니다.

## 1. 알고 싶은 것

| # | 질문 | 관련 규칙 |
|---|---|---|
| Q1 | 자율도를 올리면 개입 횟수는 줄어드는데, 통제감도 같이 줄어드는가 | R2 |
| Q2 | 결제 직전에 가격이 바뀌었을 때 사람이 알아채고, 의도대로 고르는가 | R4 |
| Q3 | 에이전트가 멈추고 물을 때 "왜 지금 묻는지" 이해하는가 | R5, R6 |
| Q4 | 어느 자율도를 다음에도 쓰겠다고 하는가 | R2, R3 |

## 2. 가설과 판단 기준

| 가설 | 맞다고 볼 기준 |
|---|---|
| H1. '담기만 확인'이 통제감과 재사용 의향의 균형점이다 | '다음에도 맡기겠다' 중앙값이 '담기만 확인'에서 가장 높다 |
| H2. '알아서'에서도 통제감이 크게 떨어지지 않는다. 결제 승인이 남아 있기 때문이다 | '통제감' 중앙값 차이가 '매번 확인' 대비 1점 이내다 |
| H3. 결제 직전 재확인 카드는 가격 변경을 놓치지 않게 한다 | 5명 중 4명 이상이 "가격이 바뀐 걸 알아챘다"고 답하고, 재확인에서 '바뀐 내용으로 다시 확인' 또는 '중단'을 직접 고른다 |
| H4. 질문 카드의 근거 한 줄이 이유를 설명한다 | 생각 말하기에서 "왜 물어보지?" 같은 혼란이 과제당 1회 이하다 |

5명은 통계로 일반화할 수 있는 수가 아닙니다. 수치는 방향을 보는 데만 쓰고, 판단은 관찰 메모와 함께 합니다.

## 3. 참가자

- 5명. 온라인 쇼핑을 한 달에 2번 이상 하는 사람.
- AI 어시스턴트(ChatGPT 등) 사용 경험은 섞습니다. 써 본 사람 3명, 거의 안 써 본 사람 2명.
- 디자이너·개발자는 1명까지만.
- 참가자 번호는 P01–P05. 이름과 연락처는 이 문서와 결과 파일에 남기지 않습니다.

## 4. 진행 (한 명당 약 35분)

| 시간 | 단계 | 내용 |
|---|---|---|
| 0–5분 | 안내 | 동의 확인, 생각 말하기 연습. "제품을 시험하는 것이지 당신을 시험하는 것이 아닙니다." |
| 5–8분 | 설정 | 설정 화면에서 내 사이즈를 고르게 합니다. 자율도는 과제마다 바뀐다고 알려 줍니다. |
| 8–28분 | 과제 3개 | 과제마다 약 6분 + 설문 1분 |
| 28–35분 | 마무리 인터뷰 | 아래 질문 |

### 화면 준비

- 주소: `https://shopping-agent-hitl.vercel.app/#/app?study=P01` (참가자 번호만 바꿉니다)
- 화면 위쪽 띠에 과제와 이번 자율도가 나옵니다. '과제 시작'을 누르면 쇼핑몰이 처음 상태로 돌아가고 자율도가 맞춰집니다.
- 테스트 모드에서는 우연한 시장 변화(다른 구매자의 구매, 가격 변경)를 멈춥니다. 대신 결제 승인 카드가 뜨고 1.2초 뒤, 담긴 상품 하나의 가격을 10% 올립니다. 자율도와 상관없이 같은 지점입니다.
- 참가자는 가격 변경이 들어간다는 걸 모릅니다.

### 과제

| 과제 | 안내 문구 |
|---|---|
| T1 | 출근할 때 입을 검정 울 코트를 20만원 이하로 사 보세요. |
| T2 | 주말에 신을 화이트 스니커즈를 15만원 이하로 사 보세요. |
| T3 | 매일 들고 다닐 가방을 10만원 이하로 사 보세요. |

요청 문장은 참가자가 직접 씁니다. 안내 문구를 그대로 붙여 넣어도 됩니다.

### 자율도 순서 (라틴 방격)

과제 순서는 고정하고 자율도 순서를 돌립니다. 세 명이 한 바퀴이고, P04는 P01과, P05는 P02와 같습니다.

| 참가자 | T1 | T2 | T3 |
|---|---|---|---|
| P01, P04 | 매번 확인 | 담기만 확인 | 알아서 |
| P02, P05 | 담기만 확인 | 알아서 | 매번 확인 |
| P03 | 알아서 | 매번 확인 | 담기만 확인 |

5명이라 완전히 균형이 맞지는 않습니다. 분석할 때 자율도별 표본 수를 같이 적습니다.

### 진행자가 하지 않는 것

- 버튼 위치를 알려 주지 않습니다. 2분 넘게 막히면 "지금 무엇을 찾고 계세요?"까지만 묻습니다.
- 가격 변경을 언급하지 않습니다. 설문에서 처음 묻습니다.

### 마무리 인터뷰

1. 세 번 중 어느 방식이 가장 편했나요? 이유는요?
2. 에이전트가 멈추고 물어봤던 순간 중 기억나는 게 있나요? 그때 왜 물어본다고 생각했나요?
3. 결제까지 에이전트가 해도 된다면, 어떤 조건이면 맡기겠어요?
4. (화면에서 '설계 보기'를 켜고) 이 설명 중 실제로 느낀 것과 다른 게 있나요?

## 5. 수집하는 것

과제를 끝낼 때마다 화면이 감사 타임라인에서 아래 값을 계산해 브라우저에 저장합니다. 모든 과제가 끝나면 JSON과 CSV로 내려받습니다. 계산 방식은 `src/study/study.ts`의 `measure`이고 테스트(`study.test.ts`)로 고정돼 있습니다.

| 열 | 뜻 |
|---|---|
| durationMs | 과제 시작부터 마지막 기록까지 걸린 시간 |
| interventions | 사람이 승인·거절·답변한 횟수 |
| rejects | 거절한 횟수 |
| undos | 되돌린 횟수 |
| questions | 에이전트가 멈추고 물은 횟수 |
| injected | 가격 변경이 실제로 들어갔는지 (결제 단계까지 가지 않으면 false) |
| priceResponse | 결제 직전 재확인에서 고른 것: refresh(바뀐 내용으로 다시 확인) / stop(중단) / none |
| outcome | done / cancelled / failed / none |
| orders | 이번 과제에서 생긴 주문 수 |
| predictable, control, again | 설문 1–7점 |
| noticed | 가격 변경을 알아챘는지: yes / no / unsure |
| memo | 참가자 한 줄 메모 |

### 과제 후 설문 (7점 척도)

1. 에이전트가 다음에 무엇을 할지 예상할 수 있었다
2. 내가 통제하고 있다고 느꼈다
3. 다음에도 이 방식으로 맡기겠다
4. 과제 중에 가격이 바뀐 걸 알아챘나요? (네 / 아니요 / 잘 모르겠다)

### 진행자 관찰 메모

과제마다 아래만 적습니다. 시간과 함께 짧게.

- 멈칫한 곳 (3초 이상 손을 멈춤)
- "왜?"가 나온 곳
- 승인 카드를 읽지 않고 누른 것으로 보이는 곳
- 설계 원칙과 다르게 이해한 곳 (예: "알아서면 결제도 하는 줄 알았다")

## 6. 분석

1. CSV 5개를 합칩니다.
2. 자율도별로 개입 횟수, 시간, 설문 세 문항의 중앙값과 범위를 냅니다. 평균은 쓰지 않습니다.
3. H3은 injected가 true인 과제만 봅니다. noticed와 priceResponse를 함께 봅니다. "알아챘다"고 했는데 none이면 재확인 전에 중단한 경우입니다.
4. 관찰 메모를 규칙(R1–R9)별로 묶습니다. 한 규칙에 혼란이 2명 이상 모이면 그 화면을 고칠 후보로 올립니다.
5. 결과는 케이스 스터디의 IMPACT 표에 "사용성 테스트" 행으로 추가합니다. 가설이 틀렸으면 틀렸다고 씁니다.

## 7. 동의와 익명화

- 시작 전에 구두로 동의를 받습니다: 화면과 목소리 녹화 여부, 기록은 참가자 번호로만 남는다는 것, 언제든 그만둘 수 있다는 것.
- 결제는 실제로 일어나지 않습니다. 카드 정보나 개인 정보를 입력하는 단계가 없습니다.
- 내려받은 파일 이름은 `nod-study-P01.csv` 형식입니다. 메모 칸에 이름이 들어가면 지우고 저장합니다.
- 녹화 파일은 분석이 끝나면 지웁니다.

## 8. 참가자마다 끝나고 할 일

- 화면 띠의 'CSV 내려받기'와 'JSON 내려받기'를 누릅니다.
- 같은 브라우저로 다음 참가자를 받으면 주소의 참가자 번호만 바꿉니다. 기록은 번호별로 따로 저장됩니다.
